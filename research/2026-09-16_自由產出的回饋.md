## 一、不重複造輪子：回饋本身的實證，`research/2026-09-06_SOLO_F_回饋的統合分析.md` 已經查得很完整

那份研究（09-06，5 個主題、k 值與 N 都查到原文數字）已經回答了七個家族中 **D（AI 對話夥伴）** 家族「回饋怎麼給效果最好」的核心問題，結論已經很扎實，本篇**不重查**，直接繼承：

| 已確立的結論 | 出處（SOLO_F） |

| 回饋要指向**任務層**（這裡錯在哪、規則是什麼），⛔ 不要指向**自我層**（稱讚、評價式語句幾乎無效甚至有害） | Kluger & DeNisi 1996，k=607，d=0.41，38% 為負 |

## 二、七個家族掃過一輪（METHOD_MAP.md）

本題主要落在 **D（AI 對話夥伴）** 家族，但要跟 **A（刻意練習）** 交叉：純粹的「AI 幫你改」若沒有「先自己想、改不出來才給答案」的階梯，會退化成單純抄答案，違反 A 家族「主動提取」的核心原則。這正是 SOLO_F 第 3 節 prompt vs recast 的機制所在——**兩階段設計本身有兩條獨立證據線支持，但缺乏統合分析直接驗證這個「兩階段」組合**（SOLO_F 已誠實標注）。

## 三、技術可行性：AI 批改接進純前端網頁

### 3-1. ⭐⭐⭐ 這個問題在這個 repo 裡已經有解——`writing.html` 的既有模式

查證 `writing.html` 現有實作（[writing.html:276](writing.html)）發現：**它完全不呼叫任何 API，也沒有存任何金鑰**。
機制是：頁面組好一段批改指令（含分級評分尺與四維度），顯示在 `.prompt-box` 裡，**Owen 自己複製貼到 Claude 對話視窗**，把回覆貼回頁面。

⭐⭐⭐ **這解掉了「金鑰放哪」這個問題本身**——**不放**。前端網頁本來就不該直接嵌 API 金鑰（見下），
`writing.html` 選的「生成 prompt，人工複製貼上」是**對單人自學、零後端的專案而言最安全、成本最低、且已經在這個 repo 裡跑得通的方案**。

### 3-2. 如果真的要接「自動」的即時批改，正確做法與風險

- **⛔ 絕對不要把 API 金鑰直接寫進前端 JS**：瀏覽器端的 JS（包含打包後的 bundle、原始碼、網路請求）對使用者與任何自動掃描工具都是**完全可見**的，金鑰洩漏會導致被盜用、超額扣款甚至服務被關（業界共識，多篇資安指南一致）。
- **正確做法是伺服器端代理（proxy）**：前端呼叫自己的後端端點，後端存金鑰、轉發請求給 Anthropic/OpenAI API——但這代表**專案需要一個後端**（哪怕是 serverless function），跟現有「純靜態 GitHub Pages」架構不相容，是額外的基礎建設投入。
- **對這個專案的意義**：quest.html／writing.html 現在是純靜態頁面（GitHub Pages 部署），**沒有後端**。要做「即時 AI 批改」勢必要嘛（a）繼續用複製貼上模式（零成本、零風險、但不即時）、要嘛（b）另外架一個 serverless proxy（例如 Cloudflare Workers／Vercel Functions 的免費額度）存金鑰。

### 3-3. 費用（Claude API，2026-09 時價，供參考）
- **Haiku 4.5**：輸入 $1／百萬 token、輸出 $5／百萬 token——這一級最便宜，適合短批改任務
- 一次批改（一句話～一小段，含 prompt 說明）大約消耗數百到一千多 token 輸入、幾百 token 輸出，**單次成本落在極低（遠低於一分錢美金）的量級**——費用不是這個功能的障礙，**架構（要不要後端）才是**。

### 3-4. 法文 A2–B2 批改準確度
- ⛔ **沒有查到任何針對法文的 LLM 批改準確度研究**（搜尋 Claude/GPT-4 + DELF/TCF 批改，結果只有法檢介紹頁與泛用多語準確度頁，無一手評測）——這與 SOLO_F 第6節的空白完全吻合，**法文是徹底空白，不是本篇漏查**。
- ⭐ 唯一可用的間接證據：Claude 官方多語能力頁指出法文表現「相對英文基準 97.9% 準確」，且英譯法人工評分 96%——這是**翻譯品質**指標，不是**批改判斷力**指標，只能當作「Claude 的法文語言能力本身足夠強，不是批改品質差的原因」的弱佐證，⛔ 不能當成批改準確度的直接證據。
- **只能外推 SOLO_F 查到的英文 GEC 研究方向**：LLM 批改「文法層級」精確度高、具體度高；「內容組織層級」具體度掉很多；「不可處理錯型」（搭配、介系詞、慣用語）表現差——沒有理由預期法文會系統性優於或劣於英文，但**沒有直接證據**。

## 四、把 SOLO_F 的回饋研究翻譯成 quest.html 遊戲機制

這是本次排程新增的部分（SOLO_F 只到「回饋怎麼設計」，沒有到「遊戲怎麼包」）：

1. **兩階段回饋機制（對應 prompt→recast 的證據，SOLO_F §3-2）**：
   產出型招式（`chant` 詠唱／`shout` 吶喊）答錯或半對時，**第一次先給「任務層提示」不給答案**（例如指出「第 2 個字的動詞變位不對」而非直接show正確句）——這正好是 `typeCheck()` 現有的「第一次錯，給開頭幾個字提示，不扣血」機制**已經做對的方向**；⭐ **改用「規則提示」取代「字首提示」會更貼近 SOLO_F 的任務層回饋原則**（例如「être 現在式，tu 用 es」比「開頭是 T…」更指向任務本身），但這需要題庫額外標註規則類別，屬於後續資料工程，非本次立即可做。
2. **⛔ 不要在戰鬥畫面裡出現任何評價式訊息**：現有「命中！」「沒組對，被反擊了」都是動作描述不是評價，✅ 已經符合 Kluger & DeNisi 的「指向任務不指向自我」原則，⛔ 之後新增文案要避免「你打得不錯」這種稱讚式語句（統合分析：稱讚式回饋 d=0.09，幾乎無效）。
3. **元認知層回饋是目前系統完全沒有的一塊（SOLO_F §7 的結論）**：quest.html 目前的機制只有「任務層」（這題對不對），**沒有「你剛剛覺得自己會不會」這一層**。可操作的最小實作：戰鬥開始出招前先問一個極輕量的「這招你有把握嗎？」二選一（有把握／不確定），事後跟實際對錯比對，累積到一定次數才用溫和方式（不是分數、不是紅字）標出「最近『有把握』但答錯的比例」——⚠️ **這件事的落地形式需要跟 CLAUDE.md 的「不秀分母」鐵律、`feedback_stakes_on_character_not_person` 一起設計，本篇只確認「這塊有實證支持、目前是空的」，不在本次排程動手實作**（超出研究項範圍，留給下一個 B 項）。
4. **自由產出（trans/chant/shout）的批改，短期內維持「生成 prompt 讓 Owen 自己貼去問 Claude」的模式**（同 3-1 的發現）：quest.html 打完一場戰鬥後，戰利品區塊已經有「匯出成 Anki 卡」（B3）；可以比照 `writing.html` 的模式，在產出型招式答錯時提供一個「複製這段去問 Claude 為什麼」的按鈕（生成好 prompt，不呼叫任何 API），**零成本、零金鑰風險，直接複用本專案已驗證過的既有模式**——這是本篇能立刻落地的技術建議，列進 GAME_ROADMAP 供未來 B 項採用。

## 五、還沒回答的問題

1. **元認知層回饋（「你剛剛有把握嗎？」）的具體 UI 設計**沒有在本篇定案，需要跟現有跳過鐵律／不秀分母鐵律一起設計，留給未來 B 項。
2. **法文批改準確度的直接證據依然是零**——除非 Owen 願意手動核對幾十筆 Claude 批改 vs 自己/老師的判斷做一次小規模校準，否則這塊永遠只能外推英文文獻。
3. **serverless proxy 要不要做**沒有定案——如果 Owen 之後想要「打完戰鬥立刻在遊戲裡看到批改」而不是「複製貼去問 Claude」，就要決定要不要跨出純靜態架構這一步，這是架構層級的決定，不是本篇該下的結論。

**這對「做成遊戲機制時怎麼給」的直接回答**：任務層回饋（規則提示）已經有雛形、只需要精緻化；元認知層回饋是真空的實證缺口；自由產出的即時 AI 批改**技術上可行但需要後端**，目前最務實的做法是複用 `writing.html` 已驗證的「生成 prompt 人工貼上」模式，不需要碰金鑰或伺服器。
